# Лимит устройств — защита Pro-подписки от шеринга аккаунта

Date: 2026-07-20
Status: approved

## Мотивация

LoadLens выходит на платную подписку: появился первый потенциальный платящий пользователь
(US-диспетчер). Аккаунт — это email + пароль, ничем не привязанный к машине, поэтому один
оплаченный Pro легко раздать пятерым коллегам в офисе. Для продукта с ценой на уровне месячной
подписки это прямая потеря выручки.

Цель — **не поймать нарушителя, а сделать шеринг менее удобным, чем покупка второго места**.
Блокировки, переписка с пользователями и ложные срабатывания стоят дороже, чем недополученная
выручка с редких шеринговых пар.

## На чём строим (существующее)

- `LLAPI.clientId()` (`extension/api.js`) — UUID установки расширения в `chrome.storage.local`.
  Не синхронизируется между машинами, то есть одна установка = одно устройство. Сейчас используется
  только для обезличенной крауд-базы (`loads`, `broker_reports`) и с аккаунтом не связан.
- JWT: access 15 мин, refresh 7 дней. `users.token_version` уже даёт отзыв всех сессий разом
  (используется сменой пароля).
- `plan: 'free' | 'pro'`, выдаётся вручную через `PATCH /admin/users/:email/plan`. Биллинга нет.

## Решение

**Лимит 3 устройства на аккаунт с мягким вытеснением самого давнего.**

Отвергнуты: жёсткий лимит с ошибкой и экраном управления устройствами (требует UI и порождает
обращения в поддержку) и «одна активная сессия» (ломает легитимный сценарий «десктоп + ноутбук»).

Честный диспетчер с рабочим десктопом, ноутбуком и домашней машиной не замечает ничего.
Пятеро на одном аккаунте получают постоянную чехарду: каждый вход вытесняет коллегу, тот логинится
заново и вытесняет следующего.

### Модель данных

Новая таблица `user_devices`:

| поле | тип | назначение |
|---|---|---|
| `id` | UUID | PK |
| `user_id` | UUID | FK на `users`, каскадное удаление |
| `client_id` | TEXT | UUID установки расширения |
| `last_seen_at` | TIMESTAMP | обновляется при login и refresh |
| `created_at` | TIMESTAMP | стандартный timestamp Sequelize |

Уникальный индекс `(user_id, client_id)`.

Новая колонка в `users`: `device_evictions INTEGER NOT NULL DEFAULT 0`.

Константа `DEVICE_LIMIT = 3`.

По конвенции проекта (`synchronize: true`, миграций нет) новая колонка добавляется идемпотентным
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` в `main.ts`; таблица создаётся самим `synchronize`.

### Правила

**`login` / `register`:** upsert `(userId, clientId)` с `lastSeen = now`. Затем, если
`plan === 'pro'` и устройств больше лимита — удалить самые давние по `lastSeen`, пока не останется
`DEVICE_LIMIT`. За каждое удаление `users.device_evictions += 1`.

**`refresh`:** для `plan === 'pro'` строка `(userId, clientId)` обязана существовать. Нет строки —
устройство вытеснено, отвечаем 401. Для `plan === 'free'` строку освежаем (`lastSeen = now`) и
никогда не отказываем.

### Три следствия, зафиксированные явно

- **Устройства пишем для всех, вытесняем только у Pro.** Иначе апгрейд Free → Pro застаёт аккаунт
  с пустой таблицей и первый же refresh выкидывает пользователя со всех машин. При таком порядке
  апгрейд просто подрезает список до трёх самых свежих.
- **Вытеснение — удаление строки, а не флаг.** Отдельное состояние «забанен» не нужно: отсутствие
  строки и есть вытеснение, а повторный вход всегда возвращает устройство обратно, вытеснив
  следующее. Это и есть целевая чехарда.
- **`device_evictions` — сигнал, а не автоматика.** У честного пользователя останется нулём годами;
  у шерящейся компании набежит десятками за неделю. По нему владелец решает, кому предложить второе
  место. Автоматической блокировки по счётчику нет и не будет — заблокировать платящего клиента по
  эвристике хуже, чем не поймать шеринг.

## Транспорт и обратная совместимость

Расширение шлёт заголовок `X-Client-Id` на `/auth/login`, `/auth/register`, `/auth/refresh`.
Функция `LLAPI.clientId()` уже существует и отдаёт нужный UUID — новых сущностей на клиенте нет.

**Запрос без заголовка от Pro-аккаунта отклоняется** (401, `reason: "client_id_required"`,
текст `"Please update the LoadLens extension to continue."`).

Альтернатива — пропускать такие запросы — отвергнута: гейт обходился бы удалением одного заголовка.
Цена выбранного варианта сейчас нулевая (Pro выдаётся руками, таких аккаунтов единицы), а через
полгода была бы реальной. Chrome Web Store обновляет расширения сам, так что для живого
пользователя это разовое неудобство.

Free-аккаунты без заголовка работают как раньше — трение на этапе знакомства с продуктом не нужно.

## Что видит пользователь

401 на refresh возвращает `{ message, reason }`, где `reason` ∈ `device_limit` | `client_id_required`.

Текст при вытеснении:

> Signed out — your account was used on another device. Pro covers up to 3 devices.

`LLAPI` при получении `reason` на refresh чистит токены и передаёт текст в существующий вывод ошибки
секции аккаунта попапа. Нового UI не появляется.

**`reason` — отдельное поле, а не разбор строки сообщения.** Клиент обязан различать «токен протух»
(молча уводим на экран входа) и «тебя вытеснили» (показываем причину). Разбор по тексту ломается при
первой же правке формулировки — тем более сразу после полного перевода UI на английский.

## Админка

В `GET /admin/users/stats` добавляются два поля: текущее число устройств и накопленный
`device_evictions`. Страница `/admin.html` показывает их колонками. Это весь интерфейс наблюдения
за шерингом.

## Тестирование

Решение о вытеснении выносится в чистую функцию без БД и без Nest:

```
decideDevices(devices, clientId, plan, limit) -> { keep, evict[] }
```

Юнит-тесты на неё:
- устройство уже известно — слот не тратится, `lastSeen` обновляется;
- свободный слот — просто добавляется;
- переполнение у Pro — вытесняется самое давнее по `lastSeen`;
- переполнение у Free — не вытесняется ничего;
- апгрейд Free → Pro с пятью устройствами — подрезает до трёх самых свежих;
- порядок вытеснения именно по `lastSeen`, а не по `createdAt`.

Поверх — спеки на `login`/`refresh` в стиле существующих `auth.service.spec.ts`: 401 с правильным
`reason`, инкремент `device_evictions`, отсутствие отказов для Free.

## Вне объёма (YAGNI)

- Экран управления устройствами в попапе — договорились на мягкое вытеснение без UI.
- Анализ IP и геолокации: у диспетчеров VPN и мобильные сети дают ложные срабатывания, а пользы
  поверх лимита устройств почти нет.
- Автоблокировка по счётчику вытеснений.
- Интеграция с биллингом — `plan` по-прежнему выставляется вручную.

## Известное ограничение

`clientId` живёт в `chrome.storage.local` и полностью под контролем клиента. Технически подкованный
пользователь может вытащить UUID и прописать его коллегам — тогда пятеро выглядят одним устройством
и лимит не сработает. Закрыть это можно только детекцией одновременных сессий (один `clientId`
работает из двух мест в одну минуту), а это отдельный, более тяжёлый дизайн с состоянием в горячем
пути запроса.

Размен сознательный: барьер поднимается с «дай пароль» до «дай пароль и полезь в потроха
расширения». Первое делают не задумываясь, второе — почти никогда, тем более в отрасли, где каждый
пользователь и так платит DAT за собственную подписку. Если `device_evictions` покажет, что шеринг
всё же массовый, детекция одновременных сессий станет следующим шагом — на тех же данных, без
переделки сделанного.
