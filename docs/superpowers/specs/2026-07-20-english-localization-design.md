# English localization — design

Date: 2026-07-20
Status: approved

## Мотивация

Потенциальный платящий пользователь (US-диспетчер) написал: *«can you make an english version of this
extension? i want webhook notifications when load pops up for DAT. if it works good im willing to pay a
subscription»*.

DAT One и Truckstop — рынок США. Все реальные платящие пользователи англоязычные, русский UI —
минус к конверсии, а не фича. Особенно критично то, что `manifest.json` (`name`/`description`) —
русский: это витрина Chrome Web Store и `chrome://extensions`, первое, что читает клиент.

Webhook-уведомления — **вне объёма этой спеки**, дизайн вынесен отдельно
(`2026-07-20-alert-webhook-channel-design.md`). Локализация выкатывается первой: она занимает часы,
а не дни, и позволяет ответить клиенту реальным результатом.

## Решение

**Переезд целиком на английский, без i18n-слоя.** Не `chrome.i18n`, не рантайм-словарь — прямая
замена строковых литералов.

Обоснование: RU-локаль пришлось бы поддерживать вечно ради одного пользователя (автора), а любой
i18n-слой — это лишние ключи, лишний JSON и лишняя точка рассинхрона между кодом и словарём.
Если позже понадобится второй язык, `chrome.i18n` вводится отдельной задачей поверх уже
англоязычной кодовой базы — это дешевле, чем тащить слой без потребителя.

**Комментарии в коде, `docs/` и `CLAUDE.md` остаются русскими** — их читает только автор,
перевод не даёт клиенту ничего и ухудшает поддерживаемость.

## Проверка

Ручная замена ~250 строк гарантированно оставляет пропуски, которые вылезут у клиента. Поэтому
локализация закрывается автоматической проверкой, а не вычиткой.

**`npm run check:lang`** — скрипт `scripts/check-lang.js`:

1. Берёт фиксированный список файлов в объёме (см. выше).
2. Срезает комментарии (`//` построчные, `/* */` блочные).
3. Падает с ненулевым кодом и списком `файл:строка`, если в остатке осталась кириллица.

Скрипт включается в `npm test`. Это даёт две вещи: подтверждение полноты перевода сейчас и защиту
от регрессии потом — любой новый русский user-facing текст роняет тесты.

**Известное ограничение:** срезание комментариев эвристическое — `//` внутри строкового литерала
(например, в URL) собьёт парсер и скроет часть строки от проверки. Отсюда правило:
**user-facing строка не живёт на одной строке с комментарием.** Ограничение осознанное: полноценный
парсер JS ради линтера — оверкилл, а правило соблюдается тривиально.

**Существующие тесты:** 10 тестов расширения и backend-спеки должны проходить без изменений
поведения. Часть тестов содержит кириллицу (в названиях кейсов и, возможно, в ассертах на
UI-строки) — те, что ассертят переведённый текст, правятся вместе с кодом; названия кейсов
остаются русскими (они вне объёма).

**Ручная проверка** после автоматической: загрузить распакованное расширение, открыть попап и
панель на живой выдаче DAT, пройти по всем секциям — автоматика ловит пропущенный перевод, но не
ловит обрезанный по ширине текст (английские строки в среднем длиннее русских на 10–15%, узкие
места — чипы в полосе под строкой груза и лейблы в `.row` попапа).

## Риски

| риск | смягчение |
|---|---|
| Английский текст не влезает в верстку чипов/попапа | ручной проход по UI после замены; при необходимости сокращать формулировки, а не менять CSS |
| Пропущенная строка | `check:lang` в `npm test` |
| Правка `content.js` (944 строки) задевает логику | замена только строковых литералов, без изменения структуры; прогон `npm test` |
| Тесты ассертят русские строки | выявляется первым же прогоном `npm test`, правится вместе с кодом |
